# PatchTST: патчинг решает проблему трансформеров

## Ключевая идея

PatchTST[^patchtst] — архитектура, которая делает две ставки, идущие вразрез с интуицией предыдущих работ:

1. **Патчинг:** вместо attention к отдельным точкам — группируем точки в патчи и работаем с патчами как с токенами
2. **Channel independence:** вместо моделирования зависимостей между каналами — обрабатываем каждый канал отдельно

Обе идеи звучат как упрощение, как отказ от выразительности. Но именно это упрощение оказывается ключом к эффективности.

**Результаты:** PatchTST показывает SOTA на стандартных бенчмарках, обходя и сложные трансформеры с cross-channel attention, и DLinear[^dlinear]. **Снижение MSE на 21%** относительно предыдущих SOTA[^patchtst].

**Название:** Patch Time Series Transformer — «временной ряд стоит 64 слов» (64 патча).

## Проблема point-wise attention

Вспомним критику трансформеров из главы 14. Одна точка ряда — просто число, не несущее почти никакой информации. Значение 150 может означать что угодно: пик, норму, выброс — всё зависит от контекста.

```
┌─────────────────────────────────────────────────────────────────────┐
│              POINT-WISE vs PATCH-WISE ATTENTION                     │
│                                                                     │
│  Point-wise (старые трансформеры):                                 │
│  ┌───┬───┬───┬───┬───┬───┬───┬───┐                                 │
│  │150│148│152│147│155│149│151│150│  ← 8 токенов, каждый = число   │
│  └───┴───┴───┴───┴───┴───┴───┴───┘                                 │
│    ↓   ↓   ↓   ↓   ↓   ↓   ↓   ↓                                   │
│  Attention сравнивает ЧИСЛА (бессмысленно!)                        │
│                                                                     │
│  Patch-wise (PatchTST):                                            │
│  ┌───────────────┬───────────────┐                                 │
│  │ 150,148,152,147│ 155,149,151,150│  ← 2 токена, каждый = ПАТТЕРН│
│  └───────────────┴───────────────┘                                 │
│         ↓                 ↓                                         │
│  Attention сравнивает ПАТТЕРНЫ (осмысленно!)                       │
└─────────────────────────────────────────────────────────────────────┘
```

Когда трансформер вычисляет attention между точками, он сравнивает голые числа. Точка 150 похожа на 148, даже если одна — пик сезона, другая — выброс. Механизм не видит локальный контекст.

**Патчинг решает радикально:** вместо точек работаем с группами последовательных точек. Патч из 16 значений — кусок ряда с видимым паттерном. Трансформер сравнивает паттерны, не числа.

## Механика патчинга

Ряд длины $L = 96$, патчи размера $P = 16$ с шагом $S = 8$:

```
Исходный ряд: [x₀, x₁, x₂, ..., x₉₅]

Патч 1: [x₀,  x₁,  ..., x₁₅]   (точки 0-15)
Патч 2: [x₈,  x₉,  ..., x₂₃]   (точки 8-23)
Патч 3: [x₁₆, x₁₇, ..., x₃₁]   (точки 16-31)
...

Количество патчей: N = ⌊(L - P) / S⌋ + 1 = ⌊(96-16)/8⌋ + 1 = 11
```

**Перекрытие (overlap):** При $S < P$ патчи перекрываются. Это даёт более плавное представление и лучшую локальность.

Каждый патч проецируется в пространство размерности $D$:

$$\mathbf{z}_i = \mathbf{W} \cdot \text{patch}_i + \mathbf{b}, \quad \mathbf{W} \in \mathbb{R}^{D \times P}$$

Добавляется позиционное кодирование:

$$\mathbf{z}'_i = \mathbf{z}_i + \text{PE}_i$$

Теперь у нас $N$ токенов размерности $D$ — стандартный вход для transformer encoder.

## Почему патчинг работает

**Богатая семантика токена.** Патч из 16 точек содержит: локальный тренд (растёт/падает), волатильность (стабильный/скачущий), форму паттерна (пик, провал, плато). Это осмысленная единица для сравнения.

**Снижение сложности.** Вместо $L$ токенов — $N \approx L/S$ токенов. Для $L=512$, $S=8$: снижение с 512 до ~64 токенов. Квадратичная сложность падает с $512^2 = 262\,144$ до $64^2 = 4\,096$ — **в 64 раза**.

**Более длинный контекст.** При фиксированном бюджете патчинг позволяет смотреть на более длинную историю. 64 токена без патчинга = 64 точки. С патчингом ($P=16$, $S=8$) = 512+ точек.

**Локальная инвариантность.** Небольшие сдвиги во времени не меняют патч радикально — встроенная аугментация.

## Channel independence: контринтуитивный выбор

Вторая ключевая идея — обрабатывать каналы независимо. Если $C$ каналов (7 категорий товаров), мы не строим один трансформер, видящий все каналы. Применяем один трансформер к каждому каналу отдельно.

```
┌─────────────────────────────────────────────────────────────────────┐
│                    CHANNEL INDEPENDENCE                             │
│                                                                     │
│  Вход: (Batch, Channels, Time) = (B, C, L)                         │
│                                                                     │
│  Channel-mixing (НЕ PatchTST):                                     │
│  ┌─────────────────────────────────────┐                           │
│  │  Один трансформер видит ВСЕ каналы  │                           │
│  │  Attention между каналами           │                           │
│  └─────────────────────────────────────┘                           │
│                                                                     │
│  Channel-independent (PatchTST):                                   │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐                               │
│  │Channel 1│ │Channel 2│ │Channel 3│ ...                           │
│  │   ↓     │ │   ↓     │ │   ↓     │                               │
│  │ Transf. │ │ Transf. │ │ Transf. │  ← Один и тот же трансформер │
│  │   ↓     │ │   ↓     │ │   ↓     │                               │
│  │ Pred 1  │ │ Pred 2  │ │ Pred 3  │                               │
│  └─────────┘ └─────────┘ └─────────┘                               │
│                                                                     │
│  Формально: (B, C, L) → reshape → (B·C, L) → Transformer           │
└─────────────────────────────────────────────────────────────────────┘
```

Кажется, мы теряем информацию о зависимостях между каналами. Если продажи A влияют на продажи B — разве модель не должна это видеть?

На практике channel independence работает по нескольким причинам.

**Меньше параметров.** Cross-channel модель должна выучить $C^2$ взаимодействий. Для 100 каналов — 10 000 взаимодействий, многие слабые или отсутствуют. CI фокусируется на временных паттернах — более robust задача.

**Лучшая генерализация.** Модель, обученная на одном наборе каналов, применяется к другому. Критично для transfer learning и foundation models.

**Достаточность локальной информации.** Для многих задач история самого ряда содержит достаточно информации. Cross-channel даёт marginal improvement, не оправдывающий сложность.

**Эмпирика.** Авторы PatchTST систематически сравнили CI и CM варианты. На большинстве датасетов CI побеждает или показывает сравнимые результаты[^patchtst].

## Архитектура в деталях

```
┌─────────────────────────────────────────────────────────────────────┐
│                    PatchTST Architecture                            │
│                                                                     │
│  Input: x ∈ ℝ^L (один канал, длина L)                              │
│       │                                                             │
│       ▼                                                             │
│  ┌─────────────────────────────────────┐                           │
│  │      Instance Normalization         │  ← (x - mean) / std      │
│  └─────────────────────────────────────┘                           │
│       │                                                             │
│       ▼                                                             │
│  ┌─────────────────────────────────────┐                           │
│  │           Patching                  │  ← L → N патчей          │
│  │   Split into patches (P, stride S)  │                           │
│  └─────────────────────────────────────┘                           │
│       │                                                             │
│       ▼  patches ∈ ℝ^(N×P)                                         │
│       │                                                             │
│  ┌─────────────────────────────────────┐                           │
│  │     Patch Embedding (Linear)        │  ← P → D                  │
│  └─────────────────────────────────────┘                           │
│       │                                                             │
│       ▼                                                             │
│  ┌─────────────────────────────────────┐                           │
│  │     + Positional Encoding           │                           │
│  └─────────────────────────────────────┘                           │
│       │                                                             │
│       ▼  tokens ∈ ℝ^(N×D)                                          │
│       │                                                             │
│  ╔═══════════════════════════════════════╗                         │
│  ║      Transformer Encoder              ║                         │
│  ║  ┌─────────────────────────────────┐  ║                         │
│  ║  │   Multi-Head Self-Attention     │  ║  × L layers            │
│  ║  │   + Feed-Forward Network        │  ║                         │
│  ║  │   + Residual + LayerNorm        │  ║                         │
│  ║  └─────────────────────────────────┘  ║                         │
│  ╚═══════════════════════════════════════╝                         │
│       │                                                             │
│       ▼  output ∈ ℝ^(N×D)                                          │
│       │                                                             │
│  ┌─────────────────────────────────────┐                           │
│  │  Flatten: N×D → N·D                 │                           │
│  └─────────────────────────────────────┘                           │
│       │                                                             │
│       ▼                                                             │
│  ┌─────────────────────────────────────┐                           │
│  │  Linear Projection: N·D → H         │  ← прогноз               │
│  └─────────────────────────────────────┘                           │
│       │                                                             │
│       ▼                                                             │
│  Output: ŷ ∈ ℝ^H (прогноз на горизонт H)                          │
└─────────────────────────────────────────────────────────────────────┘
```

**Instance Normalization.** Перед обработкой ряд нормализуется — вычитается среднее, делится на std. Модель инвариантна к масштабу. После прогноза — обратное преобразование.

**Transformer Encoder.** Стандартный из «Attention Is All You Need»[^attention]: multi-head attention, FFN, residual, LayerNorm. Никаких специальных модификаций — вся адаптация через патчинг.

**Flatten + Linear.** После трансформера — $N$ токенов размерности $D$. Конкатенируются в $N \cdot D$ и проецируются линейным слоём в прогноз $H$.

## Self-supervised pretraining

PatchTST предлагает предобучение без разметки через **masked patch prediction** — идея из BERT[^bert]:

```
┌─────────────────────────────────────────────────────────────────────┐
│                   MASKED PATCH PREDICTION                           │
│                                                                     │
│  Оригинальные патчи:                                               │
│  [Patch1] [Patch2] [Patch3] [Patch4] [Patch5] [Patch6]             │
│                                                                     │
│  После маскирования (40%):                                         │
│  [Patch1] [MASK]  [Patch3] [MASK]  [Patch5] [MASK]                 │
│                                                                     │
│  Задача модели: восстановить замаскированные патчи                 │
│  Loss: MSE между предсказанными и истинными значениями             │
└─────────────────────────────────────────────────────────────────────┘
```

**Когда полезно:**
- Много исторических данных, мало размеченных примеров
- Transfer на новый домен с ограниченными данными
- Универсальное представление для разных downstream задач

После предобучения — fine-tuning на конкретную задачу прогнозирования.

## Сильные стороны

**Эффективность на длинных горизонтах.** Патчинг позволяет обрабатывать длинные входы и делать прогнозы на длинные горизонты. На ETTh1 с H=720 PatchTST значительно обходит конкурентов[^patchtst].

**Выигрыш от больших входных окон.** PatchTST — одна из немногих моделей, которая реально улучшается при очень больших look-back окнах. Если DLinear «насыщается» после 336 шагов (дальнейшее увеличение окна не улучшает прогноз), то PatchTST продолжает улучшаться при окне в 512 или даже 1024 шага[^patchtst]. Патчинг позволяет удерживать семантику на такой глубине — трансформер видит ~64 патча независимо от абсолютной длины окна.

**Простота архитектуры.** Никаких специальных механизмов — стандартный transformer encoder + патчинг. Легко реализовать, отладить, понять.

**Transfer learning.** Channel independence + self-supervised pretraining делают PatchTST хорошим кандидатом для переноса между задачами.

**Ответ на критику DLinear.** PatchTST показал: трансформеры работают на рядах, если правильно токенизировать. Это «реабилитация» трансформеров после статьи «Are Transformers Effective?»[^survey].

## Ограничения

**Фиксированные гиперпараметры патчинга.** Размер $P$ и шаг $S$ нужно выбирать под данные. Для часовых с суточной сезонностью — патч 24. Для других — нужен другой размер. Универсального рецепта нет.

**Потеря fine-grained информации (over-patching).** Патчинг агрегирует локальную информацию. Если важны точные значения в конкретные моменты (пик в 18:00), патчинг может размыть.

**⚠️ Риск over-patching:** Если размер патча $P$ слишком велик по сравнению с частотой важных событий (резкий скачок напряжения в сети длительностью 1 шаг, flash crash на бирже), модель его «проглотит» — событие станет одной из 16 точек в патче и потеряет значимость. Для таких задач: уменьшайте $P$, увеличивайте overlap ($S \ll P$), или возвращайтесь к моделям без патчинга (N-HiTS, DLinear).

**Channel independence как ограничение.** Для данных с сильными межканальными зависимостями (взаимодополняющие товары) CI может стоить качества. Альтернативы: TSMixer, iTransformer.

**Вычислительная стоимость.** Трансформер тяжелее MLP-моделей. Для real-time inference или edge-устройств — проблема.

from neuralforecast.models import PatchTST
from neuralforecast.losses.pytorch import MAE

HORIZON = 16
INPUT_SIZE = 96

model = PatchTST(
    h=HORIZON,
    input_size=INPUT_SIZE,
    loss=MAE(),
    max_steps=1000,
    
    # Параметры патчинга
    patch_len=16,             # размер патча P
    stride=8,                 # шаг S (overlap = P - S = 8)

### Выбор параметров патчинга

```python
def suggest_patch_params(input_size, season_length):
    """
    Эвристика для выбора параметров патчинга.
    
    Правила:
    1. patch_len ≈ season_length или его делитель
    2. stride = patch_len // 2 (50% overlap) — хороший дефолт
    3. Количество патчей N должно быть разумным (8-64)
    """
    # Размер патча: близко к сезонности
    if season_length <= 24:
        patch_len = season_length
    else:
        # Для длинной сезонности — делитель
        for divisor in [24, 12, 8, 6, 4]:
            if season_length % divisor == 0:
                patch_len = season_length // divisor
                break
        else:
            patch_len = 16  # дефолт
    
    # Шаг: 50% overlap
    stride = max(patch_len // 2, 1)
    
    # Проверяем количество патчей
    n_patches = (input_size - patch_len) // stride + 1
    
    return {
        'patch_len': patch_len,
        'stride': stride,
        'n_patches': n_patches
    }

# Пример: часовые данные с суточной сезонностью
params = suggest_patch_params(input_size=168, season_length=24)
# {'patch_len': 24, 'stride': 12, 'n_patches': 13}
```

## Гиперпараметры

| Параметр | Типичные значения | Комментарий |
|----------|-------------------|-------------|
| `patch_len` | 8-48 | Зависит от сезонности данных |
| `stride` | patch_len // 2 | 50% overlap — хороший дефолт |
| `hidden_size` | 64-256 | Размерность модели |
| `n_heads` | 4-8 | Должен делить hidden_size |
| `e_layers` | 2-4 | Больше ≠ лучше (переобучение) |
| `dropout` | 0.1-0.3 | Регуляризация |

## PatchTST vs другие модели

| Критерий | PatchTST | DLinear | TSMixer | N-HiTS |
|----------|----------|---------|---------|--------|
| Channel handling | Independent | Independent | Mixing | Independent |

## Выводы

1. **Патчинг — ключ к трансформерам на рядах.** Токенизация через патчи даёт семантически богатые токены вместо голых чисел.

2. **Channel independence работает.** Контринтуитивно, но отказ от межканального моделирования часто улучшает результаты.

3. **Простота архитектуры.** Стандартный transformer encoder + правильная токенизация = SOTA.

4. **Историческое значение.** PatchTST «реабилитировал» трансформеры после критики DLinear и стал основой для многих foundation models (TimesFM, Moirai).

**Открытый вопрос:** PatchTST доказывает мощь channel independence — каждый канал обрабатывается отдельно, attention работает по времени внутри канала. Но что если направить attention в другую сторону — по каналам, а не по времени? Именно это делает iTransformer, который мы рассмотрим в следующей главе.

В следующей главе рассмотрим iTransformer — альтернативный подход, где attention применяется не по времени, а по каналам.
